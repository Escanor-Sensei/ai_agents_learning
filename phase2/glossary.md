# Phase 2 — Glossary

> Quick reference for all key terms introduced in Phase 2.  
> Terms are listed in the order you'll encounter them while studying.

---

## Function Calling / Tool Calling Terms

### Function Calling (Tool Calling)
The mechanism by which an LLM requests your code to execute a specific function with specific arguments. The LLM **never** executes the function — it only generates a JSON request. Your runtime does the actual execution.  
**Analogy**: A customer ordering from a menu — they pick the dish, the kitchen cooks it.

### Tool Schema
A JSON description of a function's name, purpose, parameters, and types. This is sent to the LLM so it knows what tools are available and how to use them.  
**Analogy**: A restaurant menu with dish names, descriptions, and prices.  
**.NET equivalent**: Swagger/OpenAPI specification for an endpoint.

### Tool Binding
The process of registering tool schemas with an LLM so it can decide when and how to call them. In LangChain: `llm.bind_tools([tool1, tool2])`.  
**.NET equivalent**: Registering services in `IServiceCollection` during DI setup.

### Tool Execution
Your runtime parsing the LLM's function call request, validating arguments, calling the actual function, and returning the result. This is the "bridge" between the LLM's decision and the real-world action.  
**.NET equivalent**: The DI container resolving a service and calling its method.

### Parallel Tool Calls
When an LLM requests multiple tool calls in a single response. Instead of calling tools sequentially, all calls can be executed simultaneously.  
**.NET equivalent**: `Task.WhenAll()` for running multiple async operations concurrently.

### Tool Registry
A pattern where tools are stored in a dictionary/lookup, allowing dynamic routing of tool calls by name. Instead of hardcoding `if tool_name == "x"` chains, you look up the tool from a registry.  
**.NET equivalent**: Service Locator pattern or DI container's `GetService<T>()`.

## Structured Output Terms

### Structured Output
Forcing an LLM to return data in a specific, predictable format (usually JSON matching a schema) instead of free-form text. Makes LLM responses machine-parseable.  
**Analogy**: The difference between writing an essay and filling out a form.  
**.NET equivalent**: Strongly-typed DTOs with Data Annotations.

### Pydantic
A Python library for data validation using Python type hints. In AI, it defines output schemas and validates LLM responses. Creates a `BaseModel` class with typed fields.  
**.NET equivalent**: A DTO class with `[Required]`, `[Range]`, `[AllowedValues]` attributes, or FluentValidation rules.

### JSON Schema
A standard format for describing the structure of JSON data — what fields exist, their types, which are required, allowed values, etc. Pydantic models are automatically converted to JSON Schema.  
**.NET equivalent**: The schema generated by Swagger/OpenAPI from your controller models.

### JSON Mode
An LLM API setting that guarantees the output is valid JSON. However, it does NOT guarantee the JSON matches a specific schema — only that it's syntactically valid.  
**Analogy**: Guaranteed to be a valid form, but the fields might not match what you expected.

### Constrained Decoding (Guided Generation)
A technique where, during token generation, the LLM's token probabilities are masked to prevent outputting tokens that would violate the schema. This enforces the schema at the generation level, not just at parsing.  
**Analogy**: A typewriter that physically locks certain keys based on what you've typed so far — you literally can't type an invalid character.

### Field Description
The `description` parameter in Pydantic's `Field()`. This text is included in the JSON Schema sent to the LLM and guides the LLM on what value to generate for each field. It's the most important part of structured output design.  
**.NET equivalent**: XML doc comments on properties, or `[Description("...")]` attribute.

### Literal Type
Python's `Literal["a", "b", "c"]` restricts a field to a fixed set of allowed values. In structured output, this ensures the LLM can only output one of the predefined options.  
**.NET equivalent**: Enum type or `[AllowedValues("a", "b", "c")]` attribute.

### Chain-of-Thought in Structured Output
Placing a `reasoning` or `thought` field before the decision fields in a Pydantic model. Since LLMs generate left-to-right, the model "thinks through" the reasoning before committing to a decision, improving accuracy.  
**Analogy**: Showing your work on a math test — the process of writing out steps helps you get the right answer.

## Error Handling Terms

### Transient Error
A temporary failure that may succeed if retried — network timeouts, rate limits (429), server errors (500/502/503). These are the only errors worth retrying.  
**Analogy**: A busy phone line — call back in a minute and it'll probably work.  
**.NET equivalent**: The types of errors Polly's `Handle<HttpRequestException>()` catches.

### Permanent Error
A failure that will NOT succeed on retry — 404 Not Found, 401 Unauthorized, 400 Bad Request, invalid parameters. Retrying these wastes time and resources.  
**Analogy**: Calling a disconnected phone number — it doesn't matter how many times you try.

### Retry
Automatically re-attempting a failed operation, usually with a delay between attempts. Only appropriate for transient errors.  
**.NET equivalent**: `Polly.Retry()` or `Polly.WaitAndRetryAsync()`.

### Exponential Backoff
A retry strategy where the wait time doubles after each failed attempt: 1s → 2s → 4s → 8s. This gives the failing service time to recover and avoids overwhelming it.  
**Analogy**: If someone's not answering the door, wait longer each time you knock instead of knocking faster.

### Jitter
Adding randomness to the backoff delay (e.g., 1.3s → 2.7s → 3.9s instead of 1s → 2s → 4s). Prevents the "thundering herd" problem where many clients retry at the exact same moment.  
**Analogy**: If 100 people all try to enter a door at once, it jams. If they spread out randomly, it flows.

### Circuit Breaker
A pattern that stops calling a failing service after a threshold of failures. Instead of wasting time on calls that will fail, it "breaks the circuit" and fails immediately. After a cooldown period, it allows one test call to check if the service recovered.  
**Three states**: Closed (normal) → Open (failing fast) → Half-Open (testing recovery)  
**.NET equivalent**: `Polly.CircuitBreakerAsync()`.  
**Analogy**: A fuse box — when too much current flows, the fuse blows and stops all current until you reset it.

### Fallback
An alternative approach used when the primary approach fails. Can be a backup API, cached data, or a default value. Fallbacks are chained: Primary → Fallback 1 → Fallback 2 → Default.  
**.NET equivalent**: `Polly.FallbackAsync()`.  
**Analogy**: If the restaurant is full, try the one next door. If that's full too, order takeout.

### Graceful Degradation
Providing a partial or lower-quality result instead of a complete failure. Better to give the user 80% of the answer than nothing.  
**Analogy**: If the highway is blocked, take a slower side road. You still get there, just slower.

### LLM-Driven Error Recovery
Instead of hardcoding retry rules, returning the error message to the LLM and letting it decide the best recovery strategy. The LLM can try different parameters, use alternative tools, or explain the failure to the user.  
**Analogy**: Instead of a fixed script, giving the error to a senior developer who can creatively figure out a workaround.

### Error Budget
A limit on total retries, tool calls, or wall time for an agent conversation. Prevents infinite retry loops and runaway costs. Example: max 10 retries total, max 15 agent steps, max 120 seconds.  
**.NET equivalent**: `CancellationToken` with timeout, or Polly's `TimeoutPolicy`.

### Idempotency
The property that an operation produces the same result whether called once or multiple times. Critical for retry safety — if you retry a "create order" operation, you don't want to accidentally create two orders.  
**.NET equivalent**: `PUT` vs `POST` in REST APIs, or idempotency keys in payment processing.  
**Analogy**: Pressing the elevator button — pressing it 10 times doesn't call 10 elevators.

### Tenacity
A popular Python library for adding retry logic to functions via decorators. It's the Python equivalent of Polly in .NET.

## Cross-Cutting Terms

### Tool Description
The natural language description of what a tool does, provided in its schema. This is the single most important factor in whether the LLM uses the tool correctly. Spend more time on descriptions than on the tool code itself.

### Validation Boundary
The point where you check data for correctness. In AI agents, validation happens at two boundaries: (1) when the LLM's tool call arguments arrive at your runtime, and (2) when tool results are returned to the LLM.  
**.NET equivalent**: Model validation at the controller boundary.

### Context Window
The maximum amount of text (tokens) an LLM can process at once. Tool schemas, conversation history, and tool results all consume context window space. Too many tools = too much schema text = less room for actual conversation.
